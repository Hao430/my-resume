# Spec: Agent 循环成本计算器

- **slug**: `agent-cost` · **URL**: `/tools/agent-cost/`
- **状态**: 待实现
- **数据源**: 无。价格表随仓库提交（见 §6）

## 1. 目标场景

用户 2026-09-13 提出的方向：不做「上下文预算模拟」（抽象、无输出），改做**算总价**。

调研（`projects/hao430cn-tools-backlog.md`）的结论是：通用 `token counter` **已被 Aiven、Cognio、
Unstract、token-calculator.net、llm-calculator、toolsana 等占满**，是红海；真正的空档在
「Agent 多步」这一侧。两者结合 → **做 agent 循环的成本，而不是单次调用的乘法**。

本工具回答的是简单计算器回答不了的问题：

- 一个 20 轮的 agent 循环到底花多少钱？
- 开缓存能省多少，几轮之后回本？
- 我的前缀长度够不够被缓存？（**低于模型最低长度会静默不缓存**）
- 每轮生成太久会不会让缓存过期？

## 2. 硬约束

| 约束 | 说明 |
|---|---|
| **纯前端、零网络** | 输入 token 数由用户提供，因此**不需要分词器**（见 §3），也不联网 |
| **不承诺精确** | 结果是估算。页面必须说明：真实账单以 API 返回的 `usage` 字段为准 |
| **价格表必须可溯源** | 每条价格带 `asOf` 日期；页面显著标注，避免读者以为是实时价 |

## 3. 为什么不需要分词器（重要设计取舍）

纯前端**算不出精确的 Claude token 数**：Anthropic 未公开分词器，官方口径是用
`count_tokens` API 计数、**不要用 tiktoken**（那是 OpenAI 的）。而 `count_tokens` 需要联网 + 密钥，
与本项目的零运行时请求约束冲突。

**因此本工具的输入是 token 数，不是文本。** 这恰好绕开了分词器问题：不需要 1MB 的 WASM 词表、
不需要联网、不需要密钥。用户从 API 的 `usage` 里拿到真实数字，或用估算值。

**非目标**：不做「贴一段文字自动算 token」。若日后要做，只能是估算，且必须在页面上标明。

## 4. 成本模型（本工具的核心，写错就是在给用户错的钱数）

### 4.1 变量

| 符号 | 含义 |
|---|---|
| `P` | 稳定前缀：system prompt + 工具定义（每轮重发，但内容不变） |
| `U` | 每轮新增输入（用户消息 / 工具结果） |
| `O` | 每轮输出（助手回复） |
| `N` | 轮数 |
| `inRate` / `outRate` | 每 1M token 的输入 / 输出单价 |

### 4.2 不缓存

第 `i` 轮请求的全部输入都要按全价计：

```
input_i = P + (i-1)(U + O) + U
cost_i  = input_i × inRate + O × outRate
```

**关键**：`(i-1)(U+O)` 这一项——历史每轮重发一次。这是成本随轮数**非线性增长**的来源，
也是简单计算器完全没体现的东西。

### 4.3 开启缓存（断点随对话前移）

自动缓存的断点落在最后一个可缓存块上，并随对话增长前移（官方文档明确）。
于是每一轮：上一轮写进缓存的整段是**读**，本轮新增的部分是**写**。

```
第 1 轮：  write = P + U                    （建立缓存，无读）
第 i≥2 轮：read  = P + (i-2)(U + O) + U
           write = U + O
```

计费倍率（**已实测查证**）：

| | 倍率 |
|---|---|
| 缓存读取 | **0.1×** 输入价（Claude Fable 5.1 为 **0.025×**） |
| 缓存写入（5 分钟 TTL） | **1.25×** 输入价 |
| 缓存写入（1 小时 TTL） | **2×** 输入价 |

回本点（官方给的算法）：5 分钟 TTL **两轮**回本（1.25 + 0.1 = 1.35 vs 未缓存的 2）；
1 小时 TTL 需要**至少三轮**（2 + 0.2 = 2.2 vs 3）。

### 4.4 两个必须显式检查的失效条件

这两条是本工具区别于简单计算器的关键，**必须在页面上直接给出结论，不能只写在说明里**：

1. **前缀低于模型的最低可缓存长度时，缓存静默不生效。** 最低长度因模型而异且
   **非单调**：Claude Opus 5 / Fable 5 系 = **512**；Opus 4.8 / Sonnet 5 = 1024；
   Opus 4.7 = 2048；Opus 4.6 / Haiku 4.5 = **4096**。
   同样 3K 的前缀，在 Opus 5 上能缓存，在 Haiku 4.5 上**静默不缓存**。
   → `P < model.minCacheable` 时，页面须明确提示「缓存不会生效」，并**不计算缓存的收益**
   （否则等于骗用户开了缓存能省钱）。

2. **TTL 从请求开始计时，生成时间也计入。** 一轮耗时 4 分钟，就只剩约 1 分钟给下一次请求。
   → 若「每轮耗时 × 轮数」的间隔超过所选 TTL，须提示缓存会过期，该轮按未命中计。

### 4.5 输出

必须给出：**不缓存总价**、**缓存总价**、**节省金额与百分比**、**回本轮数**，
以及 §4.4 两条失效条件的结论。可选：逐轮明细（前若干轮 + 末轮），让非线性增长可见。

### 4.6 token 明细（按 API 的 `usage` 口径）

除总价外，必须输出一份**按计费类别拆分的 token 明细**，让读者能把本工具的估算
与 API 实际返回的 `usage` 字段逐个对照。四类的口径与 `usage` 的对应关系：

| 类别 | 对应 `usage` 字段 | 单价 |
|---|---|---|
| 缓存命中（读取） | `cache_read_input_tokens` | 输入价 × 读取倍率（0.1，Fable 5.1 为 0.025） |
| 缓存写入（未命中但被缓存） | `cache_creation_input_tokens` | 输入价 × 写入倍率（1.25 / 2） |
| 未命中且未缓存 | `input_tokens` | 输入价全额 |
| 输出 | `output_tokens` | 输出价 |

**为什么值得单列**：缓存没生效时（§4.4 两种情况），第三类会吃掉全部输入——
这正是「以为开了缓存却一分没省」在数字上的形状。只给总价看不出这件事。

明细每类给：token 数、适用单价、小计；末尾给合计。**

### 4.7 价格表的模型覆盖

至少覆盖当前主力模型与**最低可缓存长度不同**的几代，因为该长度非单调
（512 / 1024 / 2048 / 4096），跨代对比正是本工具的价值点之一。
不收录受限访问的模型（如 Project Glasswing 专属者），避免给出读者用不上的选项。

## 5. 页面规则

- 输入：模型、轮数、前缀 tokens、每轮新增输入 tokens、每轮输出 tokens、
  每轮耗时（秒）、缓存开关（关 / 开·5 分钟 / 开·1 小时）。
- 全部实时计算（纯算术，无防抖必要）。
- **不得**把估算表述为精确金额；页面须写明「实际以 API 的 `usage` 为准」。
- 价格表标注 `asOf` 日期。

## 6. 价格数据

落在 `src/data/model-pricing.ts`（手写，随仓库提交）。每条含：
`id` / `label` / `inputPerMTok` / `outputPerMTok` / `minCacheablePrefix` / `cacheReadMultiplier` /
`cacheWriteMultiplier`（5 分钟）/ `cacheWriteMultiplier1h` / `contextWindow`。

**维护**：模型与价格会变（缓存倍率也可能调整）。改动必须同步更新 `asOf`。
价格过期的算钱工具比没有更糟——它会让人做出错误的决策。因此：
- 数据文件带 `asOf`，页面显著展示
- 新增一条测试断言 `asOf` 不超过 N 天？**不做**——那会让 CI 因时间流逝而变红。
  改为在页面上显式展示日期，把过期暴露给读者（与依赖雷达同一策略）。

## 7. 非目标

- **不做单次调用的简单乘法**。那是红海，且已被至少六家占满。
- **不做文本 → token 计数**（见 §3）。
- **不做多供应商价格对比**（OpenAI / Gemini）。保持单一供应商的准确性，避免维护面爆炸。
- **不做真实账单读取**。可能的话那是 Admin API 的领域，需要密钥，与零运行时冲突。
- **不预测**未来用量。

## 8. 已知限制

1. **是估算**。真实 token 数只有 API 的 `usage` 字段说了算；缓存命中还受工作区隔离、
   前缀字节是否完全一致等因素影响。
2. **价格会过期**。见 §6。
3. **假设缓存总是命中**（在 §4.4 两条失效条件之外）。现实中前缀出现任何字节变化
   （时间戳、非确定性工具顺序）都会静默失效。
4. **TTL 行为按「每轮耗时相同」简化**，不均等的间隔只能近似。

## 9. 验收标准

- 成本模型：断言不缓存时第 i 轮输入含 `(i-1)(U+O)`（历史重发）；
  断言缓存开启时第 1 轮只有写、第 2 轮起有读；断言 5 分钟 TTL 两轮回本、1 小时 TTL 三轮回本。
- token 明细（4.6）：断言四类 token 数之和等于该模式下实际发送与生成的 token 总数；
  断言各类小计之和等于总价（**分项必须真的加起来等于总数**，否则明细就是装饰）；
  断言缓存未生效时「未命中且未缓存」一项吃掉全部输入、命中与写入均为 0。
- 失效条件：断言 `P < minCacheablePrefix` 时页面**不显示**缓存收益，而显示「缓存不会生效」。
- 倍率：断言 Fable 5.1 的读取倍率是 0.025 而非 0.1。
- 免责：断言页面含「以 API 的 usage 为准」类表述，且不出现「精确」等承诺词。
- i18n：中英键数对齐；英文页不含中文。
- 构建：不联网（沿用依赖雷达的静态检查）。
