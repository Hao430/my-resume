一位持卡人让 Agent 买一双绿色的鞋。Agent 买了一双红色的，而且不可退。这笔钱谁来承担？

这个例子不是我编的。2026 年 4 月，美国运通的一位高管用它来解释为什么由运通给客户退款（[Digital Commerce 360](https://www.digitalcommerce360.com/2026/04/14/american-express-agentic-commerce-developer-kit-purchase-protection)）。再读一遍这句话的分量：**"Agent 做错了谁付钱"这个问题的答案，是由一家卡组织在新闻稿里发明出来的**，并且被当作差异化卖点。半年前，这个问题根本没人回答。

2025 到 2026 年，整个行业都在修让 Agent 能交易的轨道。几乎没有人在修让 Agent 能吵架的地方。

## 每一层实际交付了什么

现在有四套技术栈声称让智能体交易成为现实。看看它们在交易出错**之后**各自做了什么：

**身份与认证。** Visa 的 Trusted Agent Protocol（2025 年 10 月）与 Mastercard 的 Agent Pay 都建立在 Cloudflare 提出的 Web Bot Auth 之上：Agent 用注册密钥对 HTTP 请求签名，商家通过 Cloudflare 或卡组织直接验证调用方是不是"代表已知持卡人的已注册 Agent"。两套协议还各加了一个标签，声明这个 Agent 是在浏览还是在付款（[Cloudflare](https://blog.cloudflare.com/secure-agentic-commerce)、[Visa 规范](https://github.com/visa/trusted-agent-protocol)）。

这解决了商家的真实痛点：把有用的购物 Agent 和爬虫区分开。但它不解决客户的问题。签名只能证明 Agent **是谁**，`tag="agent-payer-auth"` 只能证明它**打算付款**。两者都不能证明"这一单就是你想要的那一单"。正如一位支付业评论者的说法：认证不等于授权，而"AI 买家犯错"的责任模型至今没有定义。

**结账。** OpenAI 的 Agentic Commerce Protocol 里那份 Delegated Payment Spec 对责任划得异常直白，原文是："OpenAI 不是 merchant of record……结算、退款、拒付与合规责任都留在商家与其支付服务商（PSP）"（[OpenAI 文档](https://developers.openai.com/commerce/specs/payment)）。Stripe 的 Shared Payment Token 是第一个兼容实现。设计本身是合理的——商家保留自己的收单、风控与客户关系。副作用是：争议最终落进了一套为"两个人类 + 一张收据"设计的拒付系统里。

**稳定币轨道。** x402 现在是 Linux Foundation 项目，它把沉睡多年的 HTTP 402 状态码真正激活：服务端报价，客户端付款，资源解锁（[x402 文档](https://docs.x402.org/core-concepts/http-402)）。官网挂着 30 天数据——7541 万笔交易、2424 万美元流水、9.4 万买家、2.2 万卖家（[x402.org](https://x402.org)，项目自报）。它同时把"交易慢、拒付、手续费"列为旧方式的缺陷。**这就是题眼**：在这条轨道上，最终性本身就是卖点——USDC 结算在设计上不可撤销，"没有拒付"是被当作消费者福利来卖的，而不是风险。

x402 并不是不懂证据——规范里有 Signed Offers and Receipts 扩展，让双方都持有"承诺过什么"的可验证记录。但它没有为**裁判**留位置。没有退款路径、默认没有托管、没有仲裁者。如果交付物不对，两个 Agent 手里握着同一份签名收据，对它的含义各执一词。

**授权意图。** Google 的 Agent Payments Protocol 加了密码学 mandate——证明用户实际授权了什么。这很有用，能解决大量"我没批准过这笔"的争执。但 mandate 证明的是授权那一刻的意图，对"结果是否匹配意图"一无所知。你授权了一笔购买，Agent 买错了型号，mandate 完好无损，钱已经出去了。

**每一层都在回答"这个 Agent 是不是真的、有没有被允许"，没有人回答"这个结果是不是错的"。**

## 这个缺口是结构性的，不是疏忽

每一笔智能体交易里，三块拼图分别握在三方手里，没有任何一方拿全：

- **用户**握着 mandate——授权了什么。
- **商家**握着证据——订单日志、履约记录、实际交付物。
- **网络或托管方**握着钱。

信用卡的争议规则假设买卖双方都是人、共用同一条时间线：你被扣款、你没拿到该拿的、发卡行把钱划回来。插入一个 Agent，链条上就多了一个没人监管的新环节：Agent 的运营方——它可能是模型厂商、钱包应用、框架，也可能是用户自己写的一段脚本。争议管理公司流传的问卷显示，责任归属的意见大致平均分布在 AI 提供方、客户、商家与支付处理方之间——这句话的体面说法是：框架还不存在。

量级让它变紧迫。Datos Insights 在 Mastercard《2025 State of Chargebacks》中的预测是：全球拒付量将从 2025 年的 2.61 亿笔升至 2028 年的 3.24 亿笔，增长 24%，金额达 417 亿美元（[Tearsheet](https://tearsheet.co/payments/with-chargeback-volume-set-to-hit-324-million-in-2028-merchants-and-issuers-need-to-find-a-way-to-protect-their-bottom-line)、[ETHOCA](https://hs.ethoca.com/chargeback-trends-global-outlook)）。而这个预测里，智能体交易还不是一个独立统计项。美国消费者银行协会已警告：Agent 的失误——买错商品、重复下单、对模糊指令的误读——可能直接压垮本已吃紧的争议处理设施。

交易越小，账越算不过来。处理一笔拒付的成本，远高于一笔 0.02 美元的 API 调用本身——而 0.02 美元正是 x402 为之而生的交易粒度。如果你的争议流程要花 25 美元，那么所有低于 25 美元的交易事实上都是最终结算，不管你有没有这个意图。

## 一个裁判层必须具备什么

如果你现在要在这些轨道上做事，这一段是可以直接落地的。五条要求，按省心程度排序：

1. **在交易之前指定裁判，而不是之后。** "到时候再说"等于"谁拿着钱谁赢"。把裁判写进协议：平台、协议本身、卡组织的保障计划，或一条明确的仲裁条款。
2. **记录带范围边界的授权。** 不是"这个 Agent 可以买鞋"，而是金额上限、有效期、商家白名单，以及真正要紧的属性（颜色、尺码、可否退货）。裁判需要的所有信息都必须在授权时就捕获，事后无法重建。
3. **让证据可被机器校验。** 签名收据、带哈希的请求/响应日志、交付证明。x402 的收据扩展方向是对的：裁判层的质量，上限由底下的证据格式决定。
4. **把争议成本压到交易金额以下。** 对微支付而言，这意味着批处理、托管窗口或信誉保证金，而不是逐笔仲裁。一个只在 500 美元以上订单生效的裁判层，不叫一层。
5. **保留人类上诉通道。** 先例很清楚：eBay 与 PayPal 从 1990 年代起就用算法处理掉大部分争议；中国的互联网法院（2017 年杭州，配合区块链存证）把常规线上纠纷交给自动化系统，北京互联网法院自 2019 年起使用 AI 辅助的虚拟法官。这些系统有一个共同点——自动化那一层便宜且快，人类那一层始终存在（[研究综述](https://www.tandfonline.com/doi/full/10.1080/13600834.2022.2088060)）。

## 谁真的在试

**卡组织，部分地试。** 运通的 Agent Purchase Protection（2026 年 4 月）是第一次真正意义上的责任转移：持卡人授权已注册 Agent，Agent 传递了经过认证的购买意图，若之后 Agent 犯错，由运通给客户退款（[运通新闻稿](https://www.americanexpress.com/en-us/newsroom/articles/innovation/american-express-debuts-agentic-commerce-experiences--ace--devel.html)）。注意它为什么做得到：注册机制、经认证的意图、加上一个本来就在跑争议处理的闭环网络。这就是裁判层的配方——由一个足够大、能吸收成本的角色实现。

**一个联盟，试得很浅。** Internet Court 是一个开放 Agent Skill，宣称要做 Agent 间商务的信任层：自然语言授权、委托权限（ERC-7710）、x402 支付、托管，以及**没有人认领的那一块——争议解决**，并且要求在合约里事先写明由谁裁决（[仓库](https://github.com/internet-court/internet-court-skill)、[官网](https://internetcourt.org)）。它那句话是我读过的对这个问题最好的概括：*支付让 Agent 能交易，裁决才让它们担责。*

关于它的成熟度我要说得准确些，因为宣传跑在了产物前面：仓库只有 **4 个提交**，最后一次推送是 2026 年 8 月 19 日。30 家"创始成员"名单横跨 MetaMask、OKX、NEAR、Starknet、x402 等，而隐私政策署名的运营方是 GenLayer Foundation——所以这是一场由单一协议厂商牵头的标准营销，目前的势能来自成员的分发能力，而不是代码。它指向的裁决方案（GenLayer、Kleros、UMA）是真实存在的协议，各自也带着自己的治理问题。

这引出了藏在简单问题背后更难的那个：**谁来裁判裁判？** 众包投票、代币持有者表决、验证者模型共识，各自都有被操纵与失效的模式——跟它们相比，人类的拒付流程反而显得久经考验。把争议交给预言机并不会取消判断，它只是把判断搬到一个问责更弱、上诉更少的地方。

## 我的结论

轨道是真的，而且能用。Agent 可以被认证、被授权、被支付；x402 的流水已经不是可以忽略的数字。但这个行业花了两年回答"Agent 能不能交易"，只花了大概两份新闻稿回答"Agent 交易错了怎么办"。

如果我要在这套栈上做事，我会默认争议是我的问题，而不是协议的问题，然后从这个前提倒推设计：有边界的授权、每一步都有签名证据、一个明确指定的裁判，以及一条写清楚的阈值——低于这个金额的交易，就当它是机器速度下的经营成本直接核销。

责任框架会在未来 18 个月内被写出来，写它的多半是卡组织与监管机构，而不是协议设计者，并且大概率会默认落在"谁拿着钱"那一方。如果你是商家，那多半就是你。
